Overview

Allows large scale creation of a variety of Open MCT views, many with integrated Conditional styling. Source files include tabular CSV, PRIDE .prl files, and Python ground control scripts (GCS). The tool outputs JSON files that are imported into Open MCT.

  1. Create and/or gather input files.
  2. Run those inputs through this tool, which then outputs an Open MCT import-ready JSON file.
  3. Import that JSON file into Open MCT in the environment and location desired.

The tool also provides a capability to extract telemetry paths from GCS scripts and PRIDE PRL files into a CSV output.

Matrix Layout Beta

What It Does

  • Uses input CSV files, one that defines conditionals and others for Display Layouts; one or more Display Layouts are created as a result.
    • Multiple Condition Sets can be created in a single file with unlimited Conditions; Conditions can include unlimited criteria.
    • The matrix layout file(s) define a grid with variable column widths and row heights and can display alphanumerics, Condition Widgets and text objects. All conditionals used in the layout files must be present in the Conditionals CSV file.
    • Named style "presets" can be defined and imported in a style presets CSV file. Style presets can be referred to and used in a Display Layout file, or styles can be defined and applied directly.
    • Elements can be statically and/or conditionally styled.
  • A LAD Table for each Display Layout file that contains the telemetry parameters used in that layout.
  • Folders that contain the above elements.

Interface

  • Output Base Name: defines the base of names used to define output JSON files.
  • Styles: optional CSV files that defines named styles (border, foreground color, background color) that can be referenced from conditional declarations and Display Layout elements.
  • Conditionals: a CSV file that defines Condition Sets and their conditions. Not required if the Layout file isn't using conditionals.
  • Display Layouts: a CSV file that defines an Open MCT Display Layout in a rows and columns grid format.

Defines Condition Sets to be used in the matrix Display Layout. Download an example: v5.1  |  v5.0.

Column Description Example

  • all: All telemetry values must meet this condition's criteria for the condition to match.

  • xor: Only one telemetry value can meet this condition's criteria for the condition to match.

Multiple Parameters in a Condition Set

A Condition Set can watch more than one telemetry parameter. List every path in the setTelemetry cell, comma-separated, with the whole cell in double quotes and no spaces after the commas. Additional conditions are added on following rows that leave setName and setTelemetry blank. A criterion's telemetry value of any or all is combined with the condition's trigger (any, all, not, xor) to evaluate across the listed parameters; a criterion can also name one specific parameter by its full path.

setName setTelemetry condName criteria output trigger
CS AppF anyLock "/Spacecraft/AppF/carrierLock,/Spacecraft/AppF/bitSyncLock" condAnyLock {telemetry:any,operation:enumValueIs,input:[1],metadata:value} LOCKED any
    condBothLock {telemetry:all,operation:enumValueIs,input:[1],metadata:value} BOTH LOCKED all

Both parameters are added to the Condition Set's composition; the tool appends a Default condition automatically. See the v5.1 example CSV.

Condition Criteria Arguments

Conditions allow any number of criteria to be defined per condition.  Arguments are defined in a JSON-like string format, in this form: { property:value,property:value,etc. } Note that both property names and values don't use quotes around them.

Argument Property Description Example
telemetry any, all or a full path to a specific telemetry point {telemetry:all}
{telemetry: /Spacecraft/subsystem/paramter1}
operation One entry from the set of available Operations; see "Condition Operation and Inputs" below for details. {operation:greaterThan}
{operation:textContains}
input Inputs appropriate for the chosen operation. Values here must be enclosed in square brackets [ ], even when the input is a string. See "Condition Operation and Inputs" below for details. {input:[-10,10]}
{input:[foo]}
metadata 'value' when evaluating any telemetry values, 'dataReceived' when operation is ifDefined, isUndefined, etc. See "Condition Operation and Inputs" below for details. {backgroundColor:#660000}

Display Layouts CSV Input File

The Display Layouts CSV file defines a grid with variable column widths and row heights. Download an example: JSON format (v5.1)  |  Legacy format (v5.0). Both produce the same layout; see Cell Format: JSON and Legacy below.

  • Row 1 defines the width of columns in the grid, in layout grid units.
  • Column A defines the height of each row in the grid, in layout grid units.
  • Cell A1 contains 3 comma-separated values that control the grid dimensions and item margin:
    • The first two values are the desired layout grid dimensions, which are the basis for grid units.
    • The last value is the amount of margin between columns and rows, in grid units.
    • For example, "1, 1, 4" will create a Display Layout with settings of grid X = 1, grid Y = 1, and 4 "grid units" of margin between columns and rows.
    • If values are not provided in A1, the tool will use the default settings of 1, 1, 4.
  • Cells can contain text, or a path to a telemetry parameter.
    • A plain cell is just its text. A cell whose value starts with "/" or "~" is treated as a telemetry parameter path (an alphanumeric).
    • To add "flags" (styling, spanning, type, options, etc.) a cell becomes a small configuration object. In the default JSON cell format that object is strict JSON with a name property; see Cell Format: JSON and Legacy and Using Optional Flags below.
    • You can use "/" or "~" characters as text, but only if they are escaped. See "Escaping Text" above.
  • Your telemetry file can include parameters that are not used by the layout file, but the converse is not true: parameters used in this file MUST be present in the telemetry CSV file used for a given matrix layout.

Cell Format: JSON and Legacy

The Cell Format setting (on the Matrix Layout page) controls how the tool reads any layout cell that carries flags. It has no effect on plain text cells or bare telemetry paths — those work the same in both modes. A cell only needs a format when you add flags such as styling, spanning, a type, or options.

  • JSON (the default): the whole cell is a single, strict JSON object that includes its own name property. Every key and every string value is wrapped in double quotes; numbers and booleans are bare. For example:
    {"name":"/Spacecraft/AppF/carrierLock","type":"alpha","stylePreset":"alphaStatic"}
    Because the cell contains commas and quotes, wrap the entire cell in CSV quotes and double every quote inside it when the .csv is saved:
    "{""name"":""/Spacecraft/AppF/carrierLock"",""type"":""alpha"",""stylePreset"":""alphaStatic""}"
    Spreadsheet applications do this doubling for you when you type a normal " inside a quoted cell — it matters mainly when hand-editing a raw .csv.
  • Legacy: the older shorthand. The cell is name:{flags} — the name comes first, then a colon, then an unquoted { } block. Keys and values are not quoted. For example:
    /Spacecraft/AppF/carrierLock:{type:alpha,stylePreset:alphaStatic}

If a cell containing a { } block fails to parse in JSON mode, the tool reports the file, row and column and skips that cell. Fix the cell to strict JSON, or switch the Cell Format to Legacy.

Note: the unquoted {property:value} syntax described under "Condition Criteria Arguments" above applies to the Conditionals CSV file only. It is not JSON and is unaffected by this setting.

Procedure Displays

What It Does

  • Traverses multiple PRIDE procedure .prl files and creates Display Layout of alphanumeric parameter values and Stacked Plots for each.
    • Parameters are grouped into their steps and labeled as such.
    • Each parameter is included as an alphanumeric with a label derived from the procedure file.
    • Widths of alphanumerics can be directly set; the width of labels is automatically calculated.
    • IMPORTANT NOTE: only fully qualified paths (e.g. '/SpacecraftSystem/Subsystem/etc.') in procedures can be found and extracted; references without in descriptive text may not be found.
  • A Tabs View that contains all the generated Display Layouts.
  • A Stacked Plot per procedure with parameters used.
  • Folders that contain the above elements.

Interface

  • Output Base Name: defines the base of names used to define output JSON files.
  • Display Layout Grid: the X and Y grid dimensions to be used by generated Display Layouts.
    • Settings here are per pixel and define the scale of item widths and heights specified elsewhere. For example, using a grid of 2,2 would create a 2 x 2 grid in the layout. Items set to 200 width and 14 high would then be 400 pixels wide by 28 pixels high.
    • Using smaller numbers here mean that items can be more tightly packed. Using a grid of 1,1 would make the grid equivalent to pixels.
  • Item Margin: a single grid unit number that controls the amount of horizontal and vertical space between items in the Display Layout. Using "1" with grid set to 2,2 would create a 2 x 2 pixel space between labels and elements.
  • Alphanumeric Width: controls the width of alphanumeric elements in the layout.
  • Row Height: controls the height of text-plus-alphanumeric pairs in the layout.

Stacked Views

What It Does

  • Takes in multiple telemetry source files and creates both a Stacked Plot and a Flexible Layout for each.
  • The source file can group telemetry parameters into Overlay Plots, which become elements within the Stacked Plots and Flexible Layouts.
    • Overlay Plots of the same name will be created once, and shared amongst multiple Stacked Plots and Flexible Layouts.
    • Telemetry parameters can specify some properties like the display of limit lines, marker size and shape, and line interpolation style.
  • Folders that contain the above elements.

Interface

  • Output Base Name: defines the base of names used to define output JSON files.

Extract Telemetry

What It Does

  • Takes in multiple source files and creates CSV file outputs that list parameters, their usage and optionally if they validated against a Yamcs database.
  • Allows validation of extracted parameters if a valid Yamcs web api server connection is available.
  • IMPORTANT NOTE: only fully qualified paths (e.g. '/SpacecraftSystem/Subsystem/etc.') in PRIDE procedure files can be found and extracted; references without in descriptive text may not be found.

Interface

  • Yamcs URL allows the entry of a valid "Get Parameter" Yamcs web api URL to allow validation of extracted telemetry parameters against the mission database. When a valid URL is entered and a good connection to a Yamcs is available, the indicator to the right of the input will display "Connected", and the "Validate Telemetry" button will be enabled once telemetry has been extracted. A Yamcs connection is not required in order to extract telemetry, only to validate it.
  • Output Base Name: defines the base of names used to define output JSON files.
  • Input File Type: choose either GCS Python scripts (.py) or PRIDE procedure (.prl).
  • Choose Files allows you to select one or more of .prl or .py files to use.
  • Download Telemetry CSV downloads the resulting output CSV.
  • Validate Telemetry If a valid Yamcs URL is entered and the connection is good, this button will enable after files have been selected. Click again to validate extracted parameters.

Find / Replace

What It Does

  • Allows bulk find and replace of strings in any valid text file, such as .txt, .json, .js, .py, etc. Takes in a single source file and a CVS table file of search / replace pairs.

Interface

  • Source file uploads a source text file.
  • Find/Replace CSV uploads a two-column CSV file of values to search for and replace in the source file.
  • Download the resulting replaced text as a file.

Find / Replace CSV input file

  • The file must have a header row, but the names of the columns are not important.
  • Values in the first column will be searched for in the source file and replaced with those in the second column, same row.
